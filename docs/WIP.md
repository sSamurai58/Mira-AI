## Правила

1. Писать свободно: гипотезы, варианты, чеклисты — можно сырым текстом.
2. У каждой активной темы — заголовок и дата начала.
3. Сделали и перенесли в основные docs → **удалить** блок отсюда (не архивировать длинно).
4. Принятое решение дублировать в `MEMORY.md`; здесь не держать как «вечную» запись.
5. Секреты и содержимое `.env` сюда не писать.

### 2026-11-11 — Мысли: NousResearch/hermes-agent

Источник: https://github.com/NousResearch/hermes-agent  
Сайт/доки: https://hermes-agent.nousresearch.com  
Лицензия: MIT · Python · Nous Research · слоган «The agent that grows with you».

#### Что это

Персональный self-improving AI-агент: один core на CLI/TUI, Desktop, web, ACP и messaging gateway.  
Фишка — замкнутый learning loop: skills из опыта, самоулучшение skills, память, поиск по прошлым сессиям (SQLite FTS5), модель пользователя (Honcho).  
Не привязан к ноутбуку: можно крутить на VPS/облаке и писать из Telegram и др.

#### Возможности (кратко)

- Провайдеры моделей без lock-in (Nous Portal, OpenRouter, OpenAI, свой endpoint и др.; `hermes model`)
- TUI: multiline, slash-команды, стриминг tool-output, interrupt
- Gateway: Telegram, Discord, Slack, WhatsApp, Signal (+ др. плагины) из одного процесса
- Skills / plugins / MCP; совместимость с agentskills.io; импорт из OpenClaw/Claude Code/Codex/Cursor
- Cron-автоматизации с доставкой на платформы
- Subagents + RPC из Python-скриптов
- Terminal backends: local, Docker, SSH, Modal, Daytona, Vercel Sandbox (+ плагины)
- Research: batch trajectories для обучения tool-calling моделей
- Nous Portal — подписка «модель + tool gateway» без россыпи ключей

#### Минусы / риски

- **Тяжёлый продукт:** огромный монорепо (CLI + gateway + desktop + web + PM + куча state-модулей); высокий порог входа и сопровождения
- **Security model честный, но жёсткий:** единственная реальная изоляция от adversarial LLM — OS/контейнер; in-process allowlist/approval — эвристики. Default terminal = хост → агент ≈ права пользователя
- **Стоимость и сложность ops:** нужен LLM API (или Portal), опционально песочницы/VPS; много ключей/платформ, если не брать Portal
- **Python 3.14 как целевой** (compat шире, но тренд «новый питон») — трение на старых окружениях
- **Шум вокруг репо:** очень высокий объём issues/звёзд — сигнал популярности, но и шум/темп изменений; следить за релизами осторожно
- **Supply-chain чувствительность:** сами ужесточали exact pins после инцидента на PyPI; обновления не «поставил и забыл»
- **Не наш доменный каркас:** это агент-платформа, не «депозит→счета→доля→вывод». Для Mira — скорее внешний инструмент/референс, не основа продукта

#### Зачем нам смотреть

- Референс: один процесс + SQLite sessions/FTS, узкий core + skills на краях, `.env` = только секреты / поведение в config
- Возможный внешний помощник в разработке (не dependency приложения Mira)
- Решение «берём / не берём / только учимся» — позже в `MEMORY.md`, отсюда убрать после решения

Открытые вопросы для нас:

- Нужен ли Hermes как daily driver для разработки Mira или достаточно Cursor?
- Если пробовать — только в Docker/изоляции, не на голом хосте с прод-секретами

#### Что взять в Mira (паттерны, не форк)

Принцип: **идеи и дисциплина**, не зависимость и не копипаст монорепо. Hermes ≠ продукт Mira.

**Взять сразу (совпадает с нашим каркасом):**

| Идея из Hermes | Как в Mira |
|----------------|------------|
| Один процесс, узкий core | Уже в `ARHITECTURE`: `ui → domain → store`; не раздувать core «на всякий случай» |
| SQLite как единственное состояние | Журнал `operations` + миграции; путь из env |
| `.env` = только секреты; поведение в конфиге | Ужесточить `RULES`: `APP_ENV`/`DATABASE_PATH` ок в example; флаги UI/фич — в `config` (yaml/json), не плодить `MIRA_*` на каждое поведение |
| Explicit incomplete | Уже stubs в PRD/DESIGN; в UI — `StubBadge`, не фейковые успехи |
| Живые docs рядом с кодом | Уже MEMORY/RULES/WIP; держать как у Hermes AGENTS: коротко в корне смысла, детали в docs |

**Взять на MVP-код (когда появится store):**

| Идея | Зачем Mira |
|------|------------|
| Атомарные мутации + recovery mindset | Депозит/доля/вывод только в одной DB-транзакции; продумать «что если краш mid-write» |
| Целочисленная арифметика денег | Уже в ARHITECTURE; не float (Hermes учит осторожности к «скрытым» форматам данных) |
| Facade + siblings при росте файлов | Не ждать god-file: `store/` по темам (`accounts`, `operations`), тонкий фасад |
| Exact pins зависимостей | Lockfile + пины; обновления осознанно (supply-chain урок Hermes) |
| First-run / doctor | Простая проверка: есть БД? доступна запись? `.env` на месте? — без мастеров на 20 экранов |
| Поиск по истории (FTS5) | После появления `operations`: поиск по комментариям/типам — как у них session FTS, но для денег |

**Позже (не MVP, держать в уме):**

- Локальный «профиль» данных (отдельный файл БД / каталог) — аналог Hermes profiles
- Лёгкий scheduler внутри процесса (отчёты/напоминания) — их cron, но без мессенджеров
- Импорт/экспорт журнала (миграция данных) — дух `import-agent`, не их код
- Опциональный AI-слой поверх журнала («объясни расход») — только после стабильного домена; отдельное решение в MEMORY

**Не брать в продукт Mira:**

- Messaging gateway (Telegram/Discord/…)
- Terminal backends / sandbox / subagents / skills hub
- Learning loop, Honcho, trajectory training
- Nous Portal / lock-in на их подписку
- Сам Hermes как runtime dependency приложения

**Как использовать Hermes снаружи (опционально):**

- Только как инструмент разработки рядом с Cursor, в изоляции (Docker), без прод-секретов Mira
- Решение «ставим / не ставим» — отдельно; на архитектуру Mira не влияет
