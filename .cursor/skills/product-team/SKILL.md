# Команда продукта

Один продукт. С пользователем говорит менеджер. Он ведёт `docs/`, пишет одно поручение, роль читает только свой файл и сдаёт один артефакт обратно менеджеру.

- [manager/SKILL.md](manager/SKILL.md) — менеджер. Указания пользователя, `docs/` (PRD, ARCHITECTURE, RULES, DESIGN, TASKS, MEMORY, DECISIONS, GLOSSARY, RELEASE, RISKS), поручения ролям.
- [product/SKILL.md](product/SKILL.md) — продакт. Зачем продукт есть и что в него не входит.
- [designer/SKILL.md](designer/SKILL.md) — дизайнер. Как это выглядит, двигается и ведёт себя в каждом состоянии. Внутри: frontend-design, Impeccable, animate, animation-performance, apple-design, emil-design-eng, prototype.
- [frontend/SKILL.md](frontend/SKILL.md) — фронтенд. То, что человек открывает и трогает.
- [backend/SKILL.md](backend/SKILL.md) — бэкенд. Данные, правила и контракт, на которых держится продукт.
- [domain/SKILL.md](domain/SKILL.md) — специалист предмета. Подключается, когда ошибку в области нельзя увидеть снаружи.
- [mobile/SKILL.md](mobile/SKILL.md) — мобильный разработчик. Подключается, когда продукт живёт в телефоне как отдельная поверхность.
- [macos/SKILL.md](macos/SKILL.md) — разработчик macOS. Подключается, когда продукт живёт отдельным приложением на Mac.
- [linux/SKILL.md](linux/SKILL.md) — разработчик Linux. Подключается, когда продукт живёт отдельным приложением на рабочем столе Linux.
- [tester/SKILL.md](tester/SKILL.md) — тестировщик. Проход выпуска, секьюрити-ревью, релиз-чеклист; все находки — менеджеру.
- [devops/SKILL.md](devops/SKILL.md) — DevOps. CI, окружения, выкладка, секреты, откат.

Второго бэкенда заводят по тому же файлу `backend/SKILL.md`. Ему отдают именной кусок системы: оплата, очередь, поиск. Два бэкенда без границы куска не создают.

## Как выбрать роль

1. Открой [manager/SKILL.md](manager/SKILL.md). Менеджер превращает просьбу в одно поручение.
2. Поручение называет одну роль. Открой её `SKILL.md` и иди по нему. Остальные файлы не читай, пока сдача не требует чужого артефакта.
3. Если артефакта предыдущей роли нет, менеджер останавливает ход и называет, какого файла не хватает. Продакта не подменяй дизайном, дизайнера не подменяй вёрсткой.

| Просьба | Роль |
|---|---|
| Указание команде, приоритет, статус, кому что сделать | Менеджер |
| Что строим, для кого, в каком порядке | Продакт |
| Экран, состояние, движение, текст на кнопке | Дизайнер |
| Собрать интерфейс по уже принятому макету | Фронтенд |
| Данные, правила, API, сохранность | Бэкенд |
| Верна ли предметная логика | Специалист предмета |
| Приложение на телефоне | Мобильный разработчик |
| Приложение на Mac | Разработчик macOS |
| Приложение на Linux | Разработчик Linux |
| Проверить выпуск, баги, секьюрити, релиз-чеклист | Тестировщик |
| CI, деплой, окружения, откат | DevOps |

## Порядок сдачи

1. Менеджер в начале проекта создаёт и дальше сам ведёт `docs/` (десять файлов, включая DECISIONS, GLOSSARY, RELEASE, RISKS), записывает поручение и принимает сдачу. Без поручения роль работу не начинает.
2. Продакт пишет одностраничное решение: кто пользователь, какая работа, что входит в этот выпуск, что остаётся снаружи, как понять, что выпуск удался.
3. Дизайнер по этому решению сдаёт экраны и состояния. Каждый экран назван словами продакта.
4. Бэкенд сдаёт контракт: сущности, операции, ошибки, что хранится.
5. Фронтенд собирает экраны дизайнера на контракте бэкенда.
6. Специалист предмета читает решение и контракт до того, как фронтенд считает работу готовой, если в продукте есть область с дорогой ошибкой.
7. Мобильный разработчик повторяет те же экраны и тот же контракт на телефоне. Разработчик macOS делает это для Mac, разработчик Linux — для названного рабочего стола. Отдельный смысл продукта они не придумывают.
8. DevOps сдаёт пайплайн, окружения и откат, когда выпуск идёт к выкладке.
9. Тестировщик по команде менеджера проходит путь, секьюрити и релиз-чеклист, затем сдаёт менеджеру полный список находок и вердикт выкладки. Починку делают роли из отчёта; тестировщик код не трогает.

## Общие правила

- Пользователь говорит с менеджером. Менеджер говорит с одной ролью за ход и держит актуальными файлы в `docs/`.
- Один ход сдаёт артефакт одной роли. Смешанный ход помечает, где кончается поручение и начинается сдача.
- Имена экранов, сущностей и ошибок совпадают у всех ролей и живут в `docs/GLOSSARY.md`. Новое имя вводит продакт.
- Спор о вкусе закрывает дизайнер в пределах решения продакта. Спор о правиле данных закрывает бэкенд. Спор о том, что правда в предметной области, закрывает специалист предмета. Спор дольше хода о стеке или подходе фиксируется ADR в `docs/DECISIONS.md`.
- Готовый кусок можно открыть и пройти основной путь. Описание без прохода не считается сдачей фронтенда, мобильного разработчика, разработчика macOS и разработчика Linux.
- Отчёт тестировщика уходит менеджеру целиком: все находки, без отбора. Менеджер разносит их по ролям на починку и в `docs/RELEASE.md` / `docs/RISKS.md`.
- Выкладка в production ждет вердикта тестировщика `к выкладке` и заполненного `docs/RELEASE.md`.
- Язык ответа совпадает с языком пользователя. Имена в коде остаются теми, что стоят в контракте.
